## Summary

The best fit for this site today is the existing native Maze anchor carrying the existing exact public `readingId` until a separately proved URL/privacy slice changes it. That keeps ordinary, modified, copied, and legacy navigation on the browser's normal multi-page lifecycle and preserves the current A-at-ingress behavior. It does not solve the later shared-handoff overwrite, which remains a known-red ownership defect already captured by the baseline.

The latest generic Edge 154.0.4258.53 evidence shows that one *complete* history marker can carry exact A through launch, reload, and manual recovery after a cancelled navigation. That corrects the earlier pending-marker stop: a completed marker is not automatically partial. The completed native control confirms the multi-page fit problem is specific to the proposed `pushState` plus reload transport: a native anchor arrives at the destination and Back restores the source URL with its source document, while `pushState` plus reload arrives at the destination and Back shows the source URL with the destination document still present. That ordinary-Back URL/document/history mismatch is a UX and navigation-correctness defect, not evidence of an exploit or a reason to invent a stronger security requirement.

## Current-state findings

- Archscry currently derives and serializes its reading context through `buildArchscryMazeContext` and `withArchscryMazeContext`; dossier render writes the shared handoff before producing real Maze anchors.
- Maze gives the URL `readingId` ingress precedence, then later `scratchpadContext()` reads the active handoff to assign `sourceContext.readingId` to a persisted Find.
- The frozen baseline proves current full A reaches Maze with A at initial ingress, but a later shared B write can own a subsequent Find. A clean A route with no private state can resolve A's catalog query while owning B. Those are current known-red ownership facts.
- The 1,002-record catalog/browser matrix is strong evidence for identity/path/thread/context catalog coverage, canonical request construction, and current navigation surfaces. It does not prove cancellation, aborted cross-document navigation, pending-marker promotion, manual recovery, or a future state protocol.

## The actual boundary

Owner requirement 12 says failed or interrupted entry preparation must be public/unassociated. The previous stop correctly found an unproven transition boundary for a *pending* history marker. It went too far when it treated every later manual recovery carrying exact A as forbidden.

There are two distinct outcomes:

| State | Assessment |
|---|---|
| A marker remains pending after an incomplete setup | It is partial state and must not attach A or B. Requirement 12 applies directly. |
| A complete browser navigation has legitimately reached Maze with exact A | The latest generic Edge evidence carries exact A through launch, reload, and manual recovery after cancellation. This can be valid exact-A continuity if the Owner accepts it; it is not the same as a partial bridge. |
| Source Archscry DOM remains visible at a Maze URL | This is a concrete multi-page UX/history mismatch, independent of whether A is exact. |

The revised question is not whether exact A is always unsafe. Product and browser evidence must decide whether a marker represents a completed cross-document transition without turning source-page state into a fake destination document. That completion finding is a proof criterion, not an additional Owner requirement.

## Browser-native alternatives

| Alternative | Fit and risk | Scope decision |
|---|---|---|
| Keep native anchors and current public `readingId` as a hold | Best immediate fit. Native pointer, keyboard, modified click, copied URL, reload, and legacy behavior remain browser-owned. It preserves existing initial A ingress but leaves the known-red later-B Find defect. | Unchanged temporary state; removal still needs later approval. |
| Same-document `pushState` plus reload | A single complete marker can preserve exact A through generic launch/reload/manual-recovery cases. However, generic Edge 154.0.4258.53 evidence now confirms normal Back restores the source URL while leaving the destination document present; a native-anchor control restores the source document correctly. | Do not resume this protocol unchanged. A revised proposal needs a transport that preserves normal Back/Forward behavior and a fresh Owner decision. |
| One `sessionStorage` record | It is per-origin and browsing context, but opener-created tabs can clone it. A stale/cancelled record and modified/new-tab behavior can therefore leak A unless consumption and eligibility are proven. It also adds persistence and cleanup ownership. | Requires a scope amendment and a protocol proof; it is not an automatic simple fix. |
| `window.name` | Cross-document tab state can survive longer than the intended handoff and has awkward opener/new-window/history semantics. It is less inspectable than a URL and does not naturally establish eligibility or cleanup. | Requires a separate proposal and Owner scope; do not use as a shortcut. |
| Navigation API | The API is recent browser surface. Root's primary-spec review and the completed generic Edge navigation show cross-document `navigate(..., { state })` does not supply this handoff: classic `history.state` is `null` and `navigation.currentEntry.getState()` is `undefined`, matching WHATWG's cross-document state treatment. | It is not a replacement transport here. Any product use needs a different, revised proposal and admission. |

The relevant standards references are the [HTML Navigation and session history APIs](https://html.spec.whatwg.org/multipage/nav-history-apis.html) and MDN's [Navigation API](https://developer.mozilla.org/en-US/docs/Web/API/Navigation_API) and [`updateCurrentEntry()`](https://developer.mozilla.org/en-US/docs/Web/API/Navigation/updateCurrentEntry). They describe state and navigation facilities; they do not replace product-specific cross-document interruption proof.

### Counterargument: repair traversal with `popstate` reload

The observed Back defect may be repairable without new persistence. Once the destination document receives `popstate` at the source pathname, it could call `location.reload()` so the browser loads the source document. A corresponding source-side traversal handler could reload when Forward selects the destination pathname. That is a technically viable alternative to declaring the original proposal impossible.

Its cost is larger than a local marker adjustment: both documents now dispatch history traversal into a document reload, and the design must define loop guards, when the URL/pathname belongs to the loaded document, fragment/query preservation, scroll restoration, page lifecycle timing, Back/Forward repeats, cancellation, modified/new-tab behavior, and legacy full URLs. It is therefore history-router/lifecycle work across the existing three owners, rather than a small single-page repair. A native cross-document navigation foundation remains preferable because the browser already owns those transitions; new persistence is not assumed unavoidable.

Before admitting that repair, a generic proof must show source Back and destination Forward settle on the correct document exactly once, preserve the intended query and history order, avoid reload loops, and retain exact A only where the evidence establishes the appropriate completed transition. Product proof must then cover native controls, keyboard/modified links, direct legacy URLs, reload, Back/Forward sequences, cancellation, and persisted Find provenance.

## Recommendation

Treat native anchors and the existing public ID as a temporary user-facing hold while a different URL transport is proved; this is not a permanent rejection of the clean-URL goal. The completed native control makes the existing path the only demonstrated normal Back behavior. Do not resume the `pushState` plus reload protocol unchanged.

If the Owner chooses to pursue clean URLs, start from a native cross-document navigation foundation and admit the smallest replacement transport proposal that can preserve normal navigation before implementation. Its generic proof must cover creation, completed navigation, cancellation, failed navigation, reload, Back/Forward, manual recovery, modified/new-tab behavior, stale-state consumption, and exact-A attribution. The `popstate` reload repair above is an available but broader lifecycle option, not a reason to assume persistence is required. Do not add session persistence, `window.name`, random keys, TTLs, boot/guide changes, or a broader application-state rewrite by default. Ordinary successful same-tab navigation must retain its approved association; this handoff does not propose a public/unassociated fallback.
