## Recommendation

The prior STOP was directionally useful but materially overstated. It correctly rejected the added pending-to-active `beforeunload`/`pagehide` protocol. It did not establish that the Owner-approved single complete marker followed by reload is infeasible.

The best bounded direction is to keep the current product unchanged and retain its native anchor/public-ID behavior temporarily while a different continuity transport is proposed and proved. Do not resume the original `pushState` plus reload method unchanged. Do not add pending/active phases, unload listeners, timers, session keys, TTLs, or a Navigation API detour.

Successful synchronous creation of the complete exact-A marker can reasonably finish **entry preparation**. A later manual reload of that entry is then the approved proposal's explicit bounded recovery and uses exact A, never B or a fabricated ID. That corrects the prior partial-marker impossibility claim. It does not rescue the method: a real Edge control shows that its Back entry can restore the source URL while retaining the destination document, violating ordinary multi-page Back behavior.

This review does not resume implementation, select a replacement protocol, issue runtime QA-3 PASS, or override Owner judgment.

## Owner wording versus later interpretation

The controlling latest requirement is:

> interrupted or failed entry preparation becomes safely public/unassociated rather than leaving an authoritative partial marker.

That protects against incomplete or invalid authority. It does not say that a complete, exact, validated A marker must be erased whenever the subsequent cross-document reload is interrupted.

The earlier Owner direction required interrupted/partial navigation testing when a pending mechanism is introduced and required that failures never produce a wrong Find. The approved proposal then specified:

- one marker containing the complete exact `readingId` and canonical selector tuple, with no phase field;
- synchronous `pushState` before default prevention;
- native clean navigation if parsing or push fails; and
- after a successful push, either explicit bounded reload recovery or immediate conversion to public/unassociated state if the reload fails.

It separately prohibited partial state that could attach B or a fabricated ID. A complete exact-A marker does neither. The phrase “a pending marker must never later become authoritative through a manual reload” first appears in the later runtime STOP packet as “Owner requirement 12.” It is a stronger derived rule, not the Owner's verbatim requirement. My prior QA adopted that stronger rule without first challenging whether a complete push had already finished entry preparation. That was the central red-team error.

The wording ambiguity remains worth recording: “failed entry preparation” can mean failure to create complete validated state, rather than cancellation after that state exists. The corrected reading prevents the team from inventing a stronger security rule. The current pause now rests on demonstrated history/UX behavior instead of that disputed rule.

## What the browser diagnostic proves—and does not prove

The assertion-bearing Edge diagnostic remains valid evidence for two narrow facts:

1. Promoting state in a cancelable `beforeunload` handler is unsafe. Dismissing the injected dialog left the old source document alive at the pushed Maze URL with active state.
2. Mutating pending to active during outgoing `pagehide` did not change the state observed by the incoming reload; the outgoing beacon saw active while the new document saw pending.

Those facts reject the two-phase unload protocol. They also expose a real UX risk: `pushState` changes the visible URL before the old Archscry document unloads, so cancellation or a stalled reload can temporarily leave Archscry content displayed at a Maze URL.

The diagnostic does not disprove a complete marker pushed before reload. Its incoming document observed the exact pre-unload snapshot—pending—so the evidence is consistent with an already-complete marker reaching Maze unchanged. It also injected a `beforeunload` handler that does not exist in any of the three admitted runtime owners. That adversarial case is useful future-regression evidence, but it is not a current production blocker by itself.

The coordinator's follow-up generic Edge 154 countercheck confirmed that a complete final marker survives normal launch and reload with exact A. When an injected `beforeunload` cancellation leaves the source document alive at the destination URL, explicit manual reload also reaches the destination with exact A. These facts directly retract the claim that every pre-document marker is partial or that exact-A recovery is inherently unsafe.

The same coordinator countercheck found a separate blocking product defect. With two generic local documents and `Cache-Control: no-cache`:

- native anchor to destination, then Back: source URL, source DOM present, destination DOM absent, state null;
- complete-marker `pushState` plus reload to destination, then Back: source URL, source DOM absent, destination DOM still present, state null.

Both assertions passed. The transport therefore creates contiguous history entries that share document state in a way that violates the site's ordinary multi-page Back expectation. This is not a hypothetical bfcache concern and does not depend on an unload listener. It is the strongest reason not to resume the original method unchanged.

## Standards fit

The classic History API supports the narrow mechanics, although the combined flow is unusual for a multi-page site:

- The HTML Standard defines `pushState` as a synchronous URL/history update that creates and activates a new entry sharing the current document state; it is not itself a navigation. Its serialized classic state belongs to that entry. See [HTML Standard: URL and history update steps](https://html.spec.whatwg.org/multipage/browsing-the-web.html#url-and-history-update-steps).
- MDN likewise states that `pushState` creates the history entry and associates its state, while the browser does not load the new URL at that call. It can throw before the handler prevents native navigation. See [History.pushState](https://developer.mozilla.org/en-US/docs/Web/API/History/pushState).
- Reload applies to the current entry/current URL. See [HTML Standard: apply the reload history step](https://html.spec.whatwg.org/multipage/browsing-the-web.html#apply-the-reload-history-step) and [Location.reload](https://developer.mozilla.org/en-US/docs/Web/API/Location/reload).
- `beforeunload` is cancelable and can impair Firefox's back/forward cache, while `pagehide` is not reliable enough to serve as a crash-commit protocol. See [beforeunload](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event) and [pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event). The best practice here is to avoid both.

The Navigation API is not a ready substitute. The current HTML Standard says `navigation.navigate({ state })` state is ignored when navigation ends cross-document, and the returned promises never settle for cross-document navigation. See [HTML Standard: initiating navigations](https://html.spec.whatwg.org/dev/nav-history-apis.html#navigation-api-initiating-navigations). The generic Edge control matched the standard: native cross-document `navigation.navigate(..., { state })` reached the destination while classic `history.state` was null and `navigation.currentEntry.getState()` was null/undefined. MDN also labels the API newly available in 2026 rather than an established compatibility baseline for this product. No Navigation API implementation should be proposed in this slice.

Classic history state can be persisted by some browsers to restore a session. “Private” here therefore means absent from the public URL and copied anchors, not secret or guaranteed memory-only. That is acceptable only if `readingId` is treated as association metadata rather than an authentication credential.

## Vanilla multi-page UX assessment

A native anchor with direct cross-document navigation is the usual and most robust multi-page pattern. That path cannot privately carry exact A under the current no-public-ID/no-new-persistence constraints. The approved handler is therefore a deliberate exception for ordinary same-tab normal-reading activation only.

The original exception would need all of the following association protections:

1. Keep a real same-origin anchor and leave Ctrl/meta/shift/alt, middle click, context-menu, target/new-window, and explore/review activations native.
2. Derive the clean canonical selector URL and build the complete versioned marker from the rendered exact A closure.
3. Call `history.pushState` with only that complete marker. Do not prevent default until the call succeeds.
4. Immediately reload the now-current clean URL. Do not introduce a pending phase or unload lifecycle listener.
5. On Maze initialization, accept A only after version, nonempty ID, exact normalized tuple, normal context, single-value selectors, and current-catalog validation. Invalid or absent state is public/unassociated and must never fall back to global B or a fabricated local ID.
6. Strip the marker from independent successor entries and reconcile entry-local memory on every history activation.
7. Preserve actual source-document restoration on Back, not merely the source URL.

If `pushState` throws, native clean navigation remains available because default was not prevented. A browser/process interruption after the complete push leaves an awkward but recoverable state: old Archscry DOM, clean Maze URL, complete exact-A marker. The generic countercheck confirms manual reload can then reach exact A. This recovery is association-safe under the corrected reading, but the normal Back regression remains.

The visible split state is the strongest objection to this design. It can confuse bookmarking, copying the address bar, refresh, and Back if the reload stalls or is canceled. The copied/bookmarked URL remains clean and opens unassociated elsewhere, which is truthful, but the current tab retains private exact A. This behavior must be shown to the Owner in a focused proof rather than hidden under “safe failure.” It is a UX tradeoff, not evidence of B attribution.

The standard permits contiguous entries to share document state and leaves document destruction versus caching to the user agent. The Edge control shows the concrete result for this design: Back changes the URL without restoring the source document. A fix would require additional route reload/hydration behavior or a different transport, with its own history, focus, scroll, failure, and owner proof. That is a revised proposal, not a small validation tweak.

## Strongest contrary argument

The strongest demonstrated case against resuming the original design is that a vanilla multi-page application must restore the source document, not just its URL, on Back. The generic native control does so, while `pushState` plus reload does not. The same method can also show one page's DOM under another page's URL during cancellation or delay. The browser offers no atomic classic-History operation that both pushes cross-document state and commits an independent destination document.

Wrong-Find safety remains a separate product-proof obligation. Tuple validation rejects mismatched routes, but same-identity A and B can share the same tuple. Only exact-A capture from the rendered source plus durable entry-local ownership, followed through an actual persisted Find after B races, can prove that the design never attributes B.

The honest answer is to keep the current method paused. The next design needs a separately approved transport or a deliberate product tradeoff. The team should not disguise the Back regression with pending phases, timers, lifecycle-event choreography, or a Maze-side reload on Back without separately proving the resulting double-navigation UX.

The strongest case for the underlying marker idea is still that the complete entry is created synchronously, carries exact selector-bound A, survives successful reload, and recovers exact A manually without B. That corrects the rationale of the prior STOP. It is insufficient to resume the implementation because it does not preserve the source document on Back.
