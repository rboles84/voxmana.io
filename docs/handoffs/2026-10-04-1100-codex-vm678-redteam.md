## Outcome

The continuity goal is sound. The attempted `pushState` followed by reload is a poor default fit for this multi-page site: an assertion-bearing native-control experiment restored the Archscry-equivalent URL on Back while leaving the Maze-equivalent document displayed. A real native link restored both correctly. No product runtime change is retained, and this review does not approve another protocol.

There was rabbit-hole drift. We added pending/active phases and unload-event promotion, then treated failure of those experiments as failure of the original single complete marker. We also strengthened the Owner's interruption requirement into a prohibition on every later manual recovery. That conclusion was overstated. A complete exact-A marker actually survived successful launch, reload, and explicit manual recovery in the isolated browser experiment. Its demonstrated normal Back defect is a distinct reason to pause the implementation technique.

Preserve the existing native links and exact reading ID temporarily while selecting and proving the smallest replacement. This is the current unchanged state, not a request to abandon URL cleanup or make ordinary same-tab launches public/unassociated. Owner explicitly rejected that regression. Public URL ID removal, legacy ingress, return hardening, integration and deployment remain unauthorized.

## What the red team supports

- Real anchors and ordinary cross-document navigation are the strongest foundation for a vanilla HTML/JS multi-page site. Keep native modified activation, keyboard activation, context menus, comparison tabs and source-page history intact.
- URL selectors should remain the portable catalog/query contract. Reading association supplies provenance, not query truth. The existing 18-fixture semantic-state contract, including dossier provenance, passed at the historical STOP candidate; it was not rerun during this unchanged-runtime review.
- A per-entry validated association and exact existing ID remain good invariants. Never read shared tab B as authority for A's Find, and never fabricate an association to hide failure. Tuple validation alone does not distinguish two readings of the same identity/path; exact source capture and entry ownership must also be proved by persisted-Find A/B races.
- The frozen 1,002-record baseline is useful catalog and current-navigation evidence. It cannot certify a future lifecycle protocol, every browser engine, or production deployment parity. Four isolated browser workers are not four public context modes; the matrix has 501 normal-reading and 501 identity-explore records.
- Keep URL privacy, Reading Finds ownership and return-navigation security as distinct repair obligations. Removing a development-derived ID from the URL improves public presentation/privacy; it does not by itself fix an unsafe return sink or make history state a secret.

## Corrected interruption assessment

The actual Owner requirement is:

> interrupted or failed entry preparation becomes safely public/unassociated rather than leaving an authoritative partial marker.

It does not literally say a later manual reload of every complete exact-A marker must be blank. The original approved proposal had one complete marker and contemplated bounded reload recovery. The earlier STOP handoffs are retained as event-time records; their impossibility claim is superseded by this correction. We must neither silently relax requirement 12 nor invent a stricter product decision for the Owner.

The diagnostic rejecting `beforeunload` promotion and outgoing `pagehide` promotion is still useful. It rejects those added protocols, not all history-based continuity. Lifecycle events are also a poor place to build a handoff commit: they are unreliable, and a `beforeunload` listener can impair Firefox's back/forward cache. See MDN's [beforeunload](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event) and [pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event) references.

## Browser observations

Root ran bounded inline Node experiments using installed `chrome-launcher`, `puppeteer-core`, and headless Edge `154.0.4258.53`. A loopback HTTP server supplied separate source and destination documents. These are generic transport diagnostics, not real Archscry/Maze execution or persisted-Find proof. No repository harness, fixture, runtime, or package file was edited.

The native control used `Cache-Control: no-cache`, distinct source/destination DOM IDs, a real anchor, no unload/history listeners, and no extra reload before Back. The comparison used the same pages with an ordinary-click handler that pushed a complete selector-bound A marker and reloaded. After arrival and Back, two animation frames preceded DOM assertions. Assertions required the correct source URL in both cases, a source document for the native control, and a destination document for the failure witness.

Independent RobQA initially had three inconclusive evaluate/timer-driven attempts: two lost the outgoing execution context, and one inspected the destination URL before proving its document had arrived. The reviewer retained those failures and then repeated the actual-anchor control with navigation wait registered before the click and an explicit destination selector wait. That controlled replay passed and independently reproduced native source restoration versus the push/reload Back defect. Server requests confirmed a destination load after the click and no new source request on Back. See the [individual QA record](2026-10-04-1100-robqa-vm678-redteam.md). A later root repeat was blocked at the loopback debugging connection (`EACCES`) and returned no additional result; it is not counted as evidence. No broad product test was substituted for the discriminating comparison.

The observed Back result is consistent with [MDN's pushState contract](https://developer.mozilla.org/en-US/docs/Web/API/History/pushState): it updates history/URL without loading the destination, and its entry initially shares the current document. We do not claim the one-engine observation proves identical behavior in Firefox/Safari. One demonstrated end-user regression is enough to reject an unchanged implementation candidate.

The [HTML Standard's initiating-navigation contract](https://html.spec.whatwg.org/multipage/nav-history-apis.html#navigation-api-initiating-navigations) explicitly ignores `navigate` state for cross-document navigation. The browser observation confirms that limitation here. New API availability does not make it a replacement for this handoff.

## Alternatives and blast radius

| Alternative | Benefit | Cost / decision |
| --- | --- | --- |
| Existing native anchors/current public ID temporarily | Preserves normal multi-page behavior while the next design is reviewed | Leaves URL verbosity and known-red late shared-B ownership unresolved. Current state only, not the final repair. |
| Original complete history marker + reload unchanged | Off-URL exact A survives reload | Demonstrated Back/document defect. Do not resume unchanged. |
| History marker plus explicit history/document repair | May repair Back/Forward within named owners | Must first prove both directions and source restoration; adds manual document/history routing and lifecycle responsibilities. Not yet disproved, approved, or validated. |
| Native navigation plus one bounded per-tab handoff | Keeps real cross-document navigation | `sessionStorage` is a familiar native primitive but opener tabs initially clone it; stale/canceled launches, consumption, independent entries and storage failure need proof. Adds persistence explicitly prohibited in this slice; requires an Owner-reviewed amendment if selected. |
| `window.name`, random-key/TTL scheme, Navigation API state | No demonstrated advantage for this contract | Adds lifetime/privacy/protocol complexity, or fails the cross-document requirement. Do not pivot by default. |

MDN documents `sessionStorage` partitioning by origin and tab, reload survival, opener copying and policy-related failures. Those are real design constraints, not a reason to assume a two-hour lifetime or a proven solution. See [Window.sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage).

The requirement combination creates a real transport tradeoff: exact private state must reach another document while public URLs stay clean, modified navigation stays native, and new persistence is forbidden. No standard API examined here provides all of that atomically. That is not proof that no small implementation can exist. Prefer a focused comparison of the two plausible transports over another round of protocol machinery.
