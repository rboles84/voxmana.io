## What changed and why

Created this attributed history packet only. VM-679 exists because VM-678 could safely shorten and secure public Archscry-to-Maze links only by retaining existing normal and gated-review Reading IDs as a temporary compatibility exception. The Owner explicitly rejected treating project/task-derived strings as permanent product identifiers and required a separate recon/design before any re-keying or migration ([VM-678 mandatory follow-up](../kanban/done/VM-678-url-security-recon.md#mandatory-deferred-follow-up); [VM-679 summary and scope](../kanban/in-progress/VM-679-product-reading-identifiers.md#summary)).

The end-user outcome sought by VM-679 is durable Reading identity: saved Reading Finds continue to belong to the reading a player launched, old saved links/data do not silently attach Finds to another reading, and public URLs no longer expose implementation-history names. It is not merely prettier URL text.

## Current contract versus superseded experiments

**Current constraints VM-679 must treat as protected until Owner approves a design:**

- Normal Reading IDs and gated-review IDs have persisted-Finds compatibility meaning; identity-explore has no Reading association.
- The ID is provenance/association data, never authorization. A new identifier must not become a security capability.
- Existing Maze parent links must remain native anchors. New tab/window, copy/paste, reload, Back/Forward, storage failure, and legacy-bookmark paths need explicit behavior, rather than inferred happy-path parity.
- Catalog selector replay, Scryfall query truth, Plain Reading labels, normal/review Finds ownership, and accepted local return construction stay protected VM-678 behavior.
- Direct-thread ingress, guide/boot changes, a continuity transport, serializer/ingress changes, and broad repair of historical A/B ownership defects are not implied by the prior work.

**Superseded or closed approaches that cannot be silently reused:** keyed history/session launch records; click interception plus pushState/reload; manual history/document routing; Navigation API state; pending/unload promotion; random-key/TTL/timer rescue; tab-scoped sessionStorage transport; automatic ingress/duplicate-policy rewrite; and direct-thread URL replay. They were either explicitly retired, falsified by browser behavior, or rejected as scope expansion.

## Decisions, blast radius, and unknowns for VM-679 design

The Owner’s specific ask is a concrete product-domain identifier design and compatibility decision packet—not a prefix replacement. The card requires a complete producer/consumer/public-exposure inventory, normal/review and old-bookmark treatment, durable opaque versus semantic alternatives, exact Finds ownership protection, rollout/failure behavior, and explicit Owner approval before implementation ([scope and acceptance criteria](../kanban/in-progress/VM-679-product-reading-identifiers.md#scope)).

The design must answer these unresolved questions with repository evidence:

1. **What is the durable Reading concept?** Is identity derived from an immutable authored reading, a stable semantic selector tuple, or a generated opaque product record? The legacy normal ID embeds a task/gate/engine/version label; a semantic replacement must not merely repackage that history. An opaque ID needs a durable authoritative producer and stable availability across rebuilds; a semantic ID needs collision/version/change rules.
2. **Which owners mint, serialize, persist, and consume it?** Reconcile every producer and reader before selecting a minting layer. The historical seams already show at least context/anchor construction, Maze handoff initialization, Finds writes, persisted store lookup/filtering, and public normal/review URLs. No presentation-only change can prove the full contract.
3. **What is the alias/migration rule for existing user data?** Legacy IDs can remain readable as aliases, be lazily resolved, or be migrated. Each option needs collision, idempotence, rollback, interrupted-write, foreign/stale local state, and wrong-reading defenses. Never attach a legacy Find to the closest-looking current reading merely because selector replay succeeds.
4. **What makes a public bookmark portable?** A copied normal URL cannot rely on tab state; it must either carry a safe durable Reading identifier or intentionally launch as public/unassociated under an Owner-approved policy. Existing normal compatibility preserved the former legacy behavior; VM-679 needs the product decision for the replacement.
5. **How does gated review differ?** Its existing literal review identifier and current dev-review memory debt must be inventoried separately. It must not be folded into normal behavior by assumption.

The blast radius therefore includes Reading identity semantics, URL serialization, Maze ingress/handoff, persisted Finds rows and lookup/filtering, return/reload/history and local data/bookmark compatibility. It does **not** by itself include catalog meanings, placement logic, Scryfall data, direct-thread support, or a browser-state transport. The player benefit is accurate continuing research across returns and saved Finds, with shareable URLs that describe the reading rather than a development milestone.

## Risks / uncertainties

- The historical A/B issue proves that identical catalog selectors can still carry different private Reading ownership. Any design that treats selectors alone as sufficient risks wrong-reading attribution.
- Existing inherited VM-678 debt remains outside this history task: direct-file Maze startup, Identity Atlas selector assertion, dev-review memory assertion, and known-red A/B facts. None is evidence that a VM-679 migration is safe.
- The historical browser evidence was primarily served HTTP/HTTPS; unsupported browser-chrome context-menu/macOS controls were not falsely certified. A future design must state its browser/support boundary.
